# 合约交易提醒系统审查与盈利模型重构

日期：2026-07-25  
审查对象：`cross-market-signal-alerts.vercel.app`、当前工作区代码、Vercel 生产部署与日志、Supabase 生产数据、现有回测与优化产物。

## 结论

当前动态做多与动态做空策略都没有可验证的正期望，生产状态应为 `HALTED`，而不是继续调参后直接交易。

生产库最近 80 条动态策略复盘，在统一扣除每笔 0.12% 模拟成本后：

| 策略 | 样本 | 净盈利笔数 | 净胜率 | 平均净收益/笔 |
| --- | ---: | ---: | ---: | ---: |
| 动态强势做多 | 32 | 9 | 28.13% | -0.8981% |
| 动态弱势做空 | 48 | 16 | 33.33% | -0.5075% |
| 合计 | 80 | 25 | 31.25% | -0.6638% |

按逐笔复利计算，这 80 笔的模拟净收益约为 -44.33%。该复利值没有考虑并发仓位，只用于显示亏损方向和量级，不能当作真实账户净值。

旧邮件常用 3% 止损、4.5% 止盈。若只计 0.12% 往返成本，净盈利约 4.38%，净亏损约 3.12%，保本胜率约为：

`3.12 / (4.38 + 3.12) = 41.6%`

实际最近 80 笔净胜率只有 31.25%，远低于保本线。

## 回测证据为什么不能支持上线

| 产物 | 结果 | 判断 |
| --- | --- | --- |
| `production_dynamic_backtest.json` | 1,730 笔；平均 -0.3736%；PF 0.775；最大回撤 -99.97% | 原始动态模型明确亏损 |
| `production_dynamic_email_backtest_latest_tp_sl_only_2026-01_06.json` | 647 笔平仓；PF 1.06；最大回撤 -88.37%；复利 -9.74% | 微弱毛优势无法形成可交易组合 |
| `production_dynamic_email_backtest_refined_tp_sl_only_2026-01_06.json` | 239 笔平仓；PF 1.23；最大回撤 -37.31% | 与筛选、调参使用同一时期，不能视为样本外 |
| `combined_strategy_optimization_2026h1.json` | 同一 2026H1 样本测试 23,240 组参数；最优受限组合 PF 1.57 | 严重多重检验；没有独立冻结期 |

优化器显示的高复利还把重叠信号当作一笔接一笔、每笔使用完整资本，忽略同时持仓、相关性、保证金和资金容量，因此不能作为账户收益预测。

## 已识别的亏损来源

### P0：会直接让负期望继续交易

1. 生产实证为负：做多、做空最近样本都亏损。
2. 动态策略绕过通用候选门槛、历史回测评分和期货执行计划。
3. 实盘闸门按“资产＋策略”计算；动态池不断换币，新币样本为零即可绕过整个策略族的亏损记录。
4. 回测使用固定持有期或 ATR 止盈止损，旧动态邮件与复盘却使用固定 3%/4.5%，研究、提醒和复盘并非同一交易。
5. 23,240 组参数在同一 2026H1 样本上选择并报告，缺少冻结的最终样本外区间。
6. 回测使用当前仍在交易的合约列表，遗漏退市币，存在幸存者偏差。
7. 回测未建模真实点差、订单簿冲击、滑点、资金费、手续费档位和延迟。
8. 复利统计忽略并发信号和相关性，夸大资本可用性。
9. 没有账户级总风险、同方向风险、相关币风险、单日亏损和回撤熔断。
10. 系统没有真实成交回报；“复盘收益”是价格路径模拟，不是账户 PnL。

### P1：会系统性高估信号质量或低估执行损失

1. 动态分数集中在 85–89，分数不是概率、期望值或校准后的置信度。
2. 顶级交易员极端同向拥挤判断原本位于“方向一致加分”之后，极端拥挤分支不可达。
3. 通用趋势过滤固定奖励 BTC 位于 SMA200 上方，未按做多/做空方向对称处理。
4. “订单簿可获取”被当作流动性通过，没有检查买卖价差、档位深度和预估冲击。
5. 动态池最低 24h 成交额只有 300 万 USDT，杠杆交易容易遭遇低流动性、插针和操纵。
6. 开仓参考价来自已收盘 K 线，发送前曾允许 2% 漂移；价格缺失时还会保留信号。
7. 复盘止损按理想止损价成交，跳空穿越止损时低估亏损。
8. 邮件恰好在 K 线边界发送时，复盘会漏掉第一根可执行 K 线。
9. 旧交易没有最长持有期，复盘可无限等待止盈或止损，资本占用被忽略。
10. K 线映射丢弃 `closeTime`，代码依靠倒数第二根推定已收盘，缺少显式时效校验。
11. 资金费使用最近已结算值；持仓量只因“能取到”而加分，未使用变化率、分位数或预测费率。
12. 任意包含“资金费率”的文字可能被当作风险警告，风险分层会被文本误判。
13. 每封最多 5 个信号按分数排序，没有同方向、同因子和高相关资产上限。
14. 邮件先发送、后写入去重记录；SMTP 成功而数据库写入失败时，重试可能重复提醒并造成重复仓位。

### P1：套利模型并非已验证的套利

1. 正资金费率的“现货多＋永续空”才是方向对冲；负资金费率需要“永续多＋可借入的现货空”。“持有稳定币＋永续多”没有现货空头腿，仍是裸多。
2. 没有验证现货借币可用量、借币利率、两腿同时成交、基差变化、强平距离和资金费持续性。
3. 套利复盘直接把预估资金费记为收益，未扣两腿费用与滑点，却会进入胜率统计。
4. 因此该策略只能是研究提醒，不能进入统一盈利统计或标为交易级。

### P1/P2：安全和运维问题

1. `CRON_SECRET` 缺失时受保护 API 原本会放行，属于 fail-open。
2. 仪表盘原本把密钥放在 `localStorage` 和查询字符串，可能进入浏览器历史、代理与运行日志。
3. 受保护响应没有显式 `no-store`。
4. Supabase Cron 模板会把 Bearer 密钥展开后存入 `cron.job`；应在执行时从 Vault 读取。
5. 当前 Vercel 生产部署来自 dirty worktree，部署与 Git 提交不可复现。
6. Vercel 最近错误视图主要被 Node 24 的 `url.parse()` 弃用警告占据，缺少可检索的业务结构化日志。
7. 运行时与 `pg_net` 都设置 60 秒，缺少超时安全余量。
8. 策略结果没有强制携带模型版本，历史规则变更前后的数据被混在一起。
9. 生产 Supabase 仍启用了两条 inverse-watch 定时任务，与仓库模板“仅手工研究”的约束漂移。

## 新盈利模型

盈利不是调高胜率，而是只在成本后期望值有统计证据时承担受限风险：

`净期望 = 胜率 × 平均盈利 - 败率 × 平均亏损 - 手续费 - 点差 - 滑点 - 资金费`

任何分数都必须由净期望和不确定性派生，不能再用手工 85–89 分替代。

### 生命周期

1. `RESEARCH`：只做逐事件回测，不发交易级提醒。
2. `PAPER`：滚动样本外通过后，运行仿真并记录本可成交价格。
3. `CANARY`：至少 30 笔纸面成交，平均净收益为正且 95% 下置信界大于 0；每笔风险 0.25%。
4. `LIVE`：至少 100 笔滚动样本外交易、30 笔纸面交易、成本 2 倍压力测试仍为正后才允许。
5. `HALTED`：任一策略族最近窗口平均净收益不为正、置信下界不为正、数据失效或达到风险阈值，立即停止新提醒。
6. `RETIRED`：跨两个独立市场阶段仍未恢复正期望，停止维护。

当前动态策略状态：`HALTED`。

### 唯一交易计划

扫描、邮件、复盘和回测必须消费同一个版本化 `TradePlan`：

- `modelVersion`
- 数据时间与信号时间
- 实际可执行入场规则
- 入场参考价
- 止损、止盈、最长持有期
- 方向
- 手续费、点差、滑点和资金费假设
- 失效条件
- 单笔风险与组合风险占用

不允许邮件回退到另一套固定止盈止损。

### 组合风险

- `CANARY`：每笔最大账户权益风险 0.25%。
- 成熟策略：单笔最多 0.50%，不得因杠杆提高风险预算。
- 全部未平仓风险最多 1.00%。
- 同方向或高相关资产合计最多 0.50%，最多两个相关仓位。
- 单日亏损 1.00%、单周亏损 2.50%、峰值回撤 5.00% 时停止新仓。
- 使用逐仓；杠杆只用于保证金效率，不能改变止损金额。

当前系统不连接账户，无法自动执行组合级限制；在接入持仓与成交数据之前，只能把交易级提醒限制为最多两个，并在人工执行端落实这些上限。

### 数据与执行门槛

- 使用当时可交易的点时 universe，并保留退市合约。
- 合约上市至少 30 天。
- 24h 名义成交额至少 5,000 万 USDT。
- 检查实时点差和止损附近深度；预估冲击必须包含在净期望中。
- 价格不可用、K 线不完整、订单簿异常或数据过期时 fail-closed。
- 发送前绝对价格漂移最多 0.30%；随后按可执行价重新计算止损和仓位。
- 止损按跳空后的可成交价格复盘。
- 资金费按持仓时段实际发生值计入。

### 验证协议

1. 以时间滚动，不以“最后 30% 交易”代替样本外。
2. 每个窗口使用训练 12 个月、验证 3 个月、测试 3 个月；窗口间至少 24 小时 embargo。
3. 参数冻结后保留最终未触碰区间。
4. 同时报告 1 倍、2 倍和 3 倍成本。
5. 用事件时间组合引擎处理并发、保证金、相关性和仓位上限。
6. 按月份、波动率、BTC 趋势、流动性和多空方向分层。
7. 使用按日/周区块 bootstrap，而不是假设每笔独立。
8. 上线门槛：净 PF > 1.20、平均净收益的 95% 下置信界 > 0、压力成本下仍为正、最大组合回撤 < 10%。

“趋势＋回踩/重测、仅限高流动性永续、按市场状态拆分多空”可以作为下一轮研究假设，但在完成上述冻结样本验证前，它不是盈利策略。

## 本次已完成的代码改造

1. 新增动态策略族级闸门；样本不足进入 `PAPER`，平均净收益非正进入 `HALTED`，95% 下置信界非正不得 `LIVE`。
2. 动态策略接入统一 ATR 执行计划，加入模型版本、最长 24 小时持有与成本字段。
3. 新复盘包含成本、时间退出、K 线边界修复和跳空止损。
4. 当前价缺失或参考价缺失时 fail-closed；默认允许漂移从 2% 收紧到 0.30%。
5. 修复极端大户拥挤分支不可达。
6. 单笔风险从 1% 降至 0.25%，每封提醒上限从 5 个降至 2 个。
7. 动态池 24h 成交额下限从 300 万提高到 5,000 万 USDT。
8. 受保护 API 在缺少密钥时 fail-closed，并添加 `no-store`。
9. 仪表盘改用 `sessionStorage` 与 Bearer 请求头。
10. Supabase Cron 模板改为运行时从 Vault 读取密钥。
11. 在 Vercel Cron API 白名单中禁用 inverse-watch，数据库遗留任务也不能再触发该提醒链路。

这些改动是止损与口径统一，不构成盈利保证。由于现有生产策略的独立证据为负，本次没有把任何新参数包装成“已经盈利”。
